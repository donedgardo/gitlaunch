<objective>
Redesign the GitHub Action to consolidate deployment status reporting into a single action invocation using a `post:` step that auto-detects job outcome.

Purpose: Eliminates the need for users to add 4 separate action calls (deploying/deployed/error/cancelled) in their workflow. The main step reports "deploying" and saves context via `core.saveState`. The post step runs automatically after the job, reads `GITHUB_JOB_STATUS` (with fallback), and reports the final outcome. The `report-build` mode is preserved for CI build reporting.

Output: Refactored `index.ts`, new `post.ts`, updated `action.yml` with `post:` entry, updated tests, `@actions/github` dependency added.
</objective>

<feature>
  <name>Consolidated GitHub Action with post-step auto-outcome detection</name>
  <files>github-action/src/index.ts, github-action/src/post.ts, github-action/src/index.test.ts, github-action/src/post.test.ts, github-action/action.yml, github-action/package.json</files>
  <behavior>
    The action operates in two modes, determined by the presence of the `environment` input:

    **Deploy mode (environment is set):**
    - Main step (`index.ts`):
      - Reads inputs: api-key, api-url, service-id, environment, build-id (defaults to github.sha via @actions/github context)
      - Saves all values to state via `core.saveState()` for the post step
      - Reports "deploying" status to GitLaunch API via PATCH
      - Sets `core.saveState("main_succeeded", "true")` on success
    - Post step (`post.ts`):
      - Runs automatically after job (post-if: always())
      - Retrieves saved state via `core.getState()`
      - If no state found (main step was skipped), exits silently
      - Determines job outcome: reads `process.env.GITHUB_JOB_STATUS`
      - Fallback: if env var missing, checks `core.getState("main_succeeded")` — if "true" report "deployed", otherwise report "error"
      - Maps outcome: success -> "deployed", failure -> "error", cancelled -> "cancelled"
      - Reports final status to GitLaunch API via PATCH
      - Errors in post step use `core.warning()` not `core.setFailed()` (don't fail the job)

    **Report-build mode (environment is NOT set, action input is "report-build"):**
    - Identical to current behavior: POST to builds endpoint, no post step needed
    - Post step exits silently when no state is found

    Cases:
    - deploy mode, job succeeds -> main reports "deploying", post reports "deployed"
    - deploy mode, job fails -> main reports "deploying", post reports "error"
    - deploy mode, job cancelled -> main reports "deploying", post reports "cancelled"
    - deploy mode, main step fails -> post detects no "main_succeeded" state, reports "error"
    - report-build mode -> posts build to API, post step is no-op
    - post step with no state -> exits silently (no API call)

  </behavior>
  <implementation>
    **IMPORTANT: All work happens inside the `github-action/` submodule directory.** Run `cd github-action` before any yarn/test commands.

    1. Add `@actions/github` dependency: `cd github-action && yarn add @actions/github`

    2. Update `action.yml`:
       - Keep existing inputs: api-key, api-url, service-id, build-id (make build-id optional with no default)
       - Keep: action input (default "report-build") for backwards compat
       - Keep: environment, status inputs (but make status optional — only needed for legacy explicit mode)
       - Add: `post: "dist/post.js"` and `post-if: "always()"` under `runs:`
       - Keep: existing outputs

    3. Refactor `index.ts`:
       - Import `@actions/github` for `github.context.sha`
       - When `environment` is set AND action is NOT "report-build": enter deploy mode
         - Use `build-id` input, falling back to `github.context.sha`
         - Save state: api_key, api_url, service_id, environment, build_id
         - PATCH deploying status to API
         - On success: `core.saveState("main_succeeded", "true")`
       - When action is "report-build": keep existing report-build logic unchanged
       - When action is "update-status" with explicit status: keep existing explicit status update logic for backwards compat

    4. Create `post.ts`:
       - Retrieve state via `core.getState()`
       - If api_key or service_id missing, return silently (main step didn't run or wasn't deploy mode)
       - Read `process.env.GITHUB_JOB_STATUS` (lowercase it)
       - Fallback: if empty, check `core.getState("main_succeeded")` — "true" means deployed, otherwise error
       - Map to GitLaunch status: success -> "deployed", cancelled -> "cancelled", else -> "error"
       - PATCH final status to API
       - Wrap in try/catch, use `core.warning()` for errors

    5. Update `package.json` build script to also build post.ts:
       ```
       "build": "ncc build src/index.ts -o dist --source-map --license licenses.txt && ncc build src/post.ts -o dist/post --source-map --license licenses.txt"
       ```
       NOTE: ncc outputs to a directory, so `dist/post/index.js` will be the post entry. Update `action.yml` post to `"dist/post/index.js"`.

    6. Update tests (see behavior section for all cases)

    **Mock patterns for tests:**
    - Mock `@actions/core`: getInput, setOutput, setFailed, info, warning, saveState, getState
    - Mock `@actions/http-client`: HttpClient with postJson, patchJson
    - Mock `@actions/github`: context.sha
    - For post.ts tests: set `process.env.GITHUB_JOB_STATUS` before importing post module
    - Use `vi.resetModules()` between tests since modules execute on import

  </implementation>
