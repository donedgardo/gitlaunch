# The Railway deploy button

This is the one-click self-host path advertised by the button in the README.
It is separate from [railway-setup.md](railway-setup.md), which covers how _we_
deploy gitlaunch.dev to Railway from CI.

The button points at `https://railway.com/deploy/gitlaunch`. That URL resolves
to a **published Railway template**, which is an artifact created once in the
Railway dashboard — it cannot be defined from this repository. Until the
template below is published, the button 404s.

## What the template has to contain

Two services. GitLaunch will not boot without a database, so a template that
ships only the app produces a crash loop on first deploy and a bad first
impression.

| Service   | Source                                             |
| --------- | -------------------------------------------------- |
| gitlaunch | Docker image `ghcr.io/donedgardo/gitlaunch:latest` |
| mongodb   | Railway's MongoDB database                         |

Sourcing from the image rather than this repository matters: the repository is
private, so a repo-backed template would fail for everyone who clicks. The
image is what makes the button work for a stranger, which is why the CI publish
job and the button are the same piece of work.

## Variables

Four are required — the app calls `loadConfig()` at boot and exits with the
list of problems if any are missing (`src/config/loadConfig.ts`).

| Variable                  | Value in the template                          |
| ------------------------- | ---------------------------------------------- |
| `MONGODB_URI`             | `${{MongoDB.MONGO_URL}}` — a service reference |
| `PUBLIC_URL`              | `https://${{RAILWAY_PUBLIC_DOMAIN}}`           |
| `COOKIE_SECRET_SIGNATURE` | `${{secret(64)}}` — Railway generates it       |
| `ENCRYPTION_KEY`          | see below                                      |

**`ENCRYPTION_KEY` cannot be auto-generated by Railway.** The config layer
requires a value that base64-decodes to exactly 32 bytes. Railway's
`${{secret(n)}}` produces `n` random characters from an alphanumeric alphabet,
which does not decode to 32 bytes for any `n` — `secret(44)` decodes to 33.
Boot fails closed on a wrong length, so the template must mark this variable as
user-supplied with the help text:

```
Generate with: openssl rand -base64 32
```

This is real friction on a "one-click" button and worth fixing at the source:
accepting a raw high-entropy string and running it through a KDF would let
Railway generate it like any other secret. Until then, the click is
one-click-plus-one-paste.

Optional but usually wanted: `USE_FAKE_GITHUB=true` for a kick-the-tyres
deploy with no GitHub App, since wiring a real App needs a callback URL that
does not exist until after the first deploy.

## Publishing it

Exact menu labels drift; the shape is stable.

1. Create a Railway project with the two services above.
2. Set the variables, marking `ENCRYPTION_KEY` as user-supplied.
3. Deploy once and confirm `/health` returns `{"status":"OK"}` — the
   healthcheck path is already set by [`railway.json`](../railway.json) for
   repo-backed deploys, but an image-backed template service needs it set in
   the dashboard.
4. Publish the project as a template and claim the slug `gitlaunch`, so the
   published URL matches the button already in the README.

## Keeping it current

The template pins `:latest`. CI moves that tag on every push to `main`, so new
deploys from the button pick up new code without republishing the template.
Existing deployments do not — Railway notifies template users of updates rather
than pushing them.

If you would rather deployments be reproducible than current, pin the template
to a `v*` tag and republish per release. That trades the free upgrade path for
knowing exactly what a given click deployed. For an alpha with a handful of
self-hosters, `:latest` is the right call.
