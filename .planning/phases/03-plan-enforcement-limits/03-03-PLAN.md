<objective>
Wire canAddRepository and canAddPrivateRepository checks into the repository creation endpoint (POST /onboarding/repositories) to close the verification gap where repository limits are not properly enforced against already-existing repos.

Purpose: The current onboarding route uses `getUsage()` with a batch-size-only check (`selectedRepos.length > limit`) that does NOT account for repositories already saved in the database. A Free user with 2 existing repos could select 2 more (batch size 2 < limit 3) and end up with 4 repos. This must use `canAddRepository()` which checks actual DB count against limits, and `canAddPrivateRepository()` for private repo blocking.

Output: Repository creation endpoint properly enforces plan limits using PlanEnforcementService methods, with tests proving the fix works for the existing+new repos scenario.
</objective>

    **Replace the current enforcement block (lines 239-276) with:**

    1. **Check total repo count**: For each selected repo, the total after saving would be `existingCount + selectedRepos.length`. Use `canAddRepository()` to check if the account can add repos. Since `canAddRepository()` checks one-at-a-time, we need to verify that `existingCount + selectedRepos.length <= limit`. The simplest approach: call the existing `getUsage()` for the limit info, then check `usage.repositories.current + selectedRepos.length > usage.repositories.limit`. But the REQUIREMENT is to use `canAddRepository`. So instead:
       - Get current repo count via `canAddRepository()` result. If current count is already at limit, `canAddRepository` returns `{allowed: false}`.
       - For batch: check if `currentRepoCount + selectedRepos.length > limit`. This requires knowing the current count AND the limit.
       - **Best approach**: Use `getUsage()` to get `current` and `limit`, then check `usage.repositories.current + selectedRepos.length > usage.repositories.limit`. ALSO call `canAddPrivateRepository()` if any selected repo is private. This uses canAddPrivateRepository from PlanEnforcementService (closing the gap) and fixes the batch math.

    **Concrete implementation:**
    ```typescript
    // Check repository limits BEFORE creating any repos
    // First: check if adding selected repos would exceed limit (accounting for existing repos)
    const usage = await planEnforcementService.getUsage(account._id);
    const totalAfterAdding = usage.repositories.current + selectedRepos.length;
    if (totalAfterAdding > usage.repositories.limit) {
      const errorMessage = `Repository limit reached (${usage.repositories.current}/${usage.repositories.limit}). Upgrade to add more repositories.`;
      return reply.view("onboarding/select-repos", {
        title: "Select Repositories",
        repositories: availableRepos,
        maxRepositories: usage.repositories.limit,
        privateReposAllowed: usage.privateReposAllowed,
        plan: usage.plan,
        error: errorMessage,
      }, { layout: "/layouts/main.hbs" });
    }

    // Second: check if any private repos are selected when not allowed
    const hasPrivateRepo = selectedRepos.some((repo) => repo.private);
    if (hasPrivateRepo) {
      const canAddPrivate = await planEnforcementService.canAddPrivateRepository(account._id);
      if (!canAddPrivate.allowed) {
        return reply.view("onboarding/select-repos", {
          title: "Select Repositories",
          repositories: availableRepos,
          maxRepositories: usage.repositories.limit,
          privateReposAllowed: usage.privateReposAllowed,
          plan: usage.plan,
          error: canAddPrivate.reason,
        }, { layout: "/layouts/main.hbs" });
      }
    }
    ```

    This changes:
    - Repo count check: `selectedRepos.length > limit` → `current + selectedRepos.length > limit` (fixes the gap)
    - Private repo check: `!usage.privateReposAllowed` → `canAddPrivateRepository()` (uses PlanEnforcementService method)
    - Error messages now come from PlanEnforcementService patterns (consistent with service/environment enforcement)
