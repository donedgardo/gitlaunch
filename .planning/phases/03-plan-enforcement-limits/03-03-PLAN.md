<objective>
Fix batch repo limit check to account for existing repos and wire canAddPrivateRepository into the repository creation endpoint (POST /onboarding/repositories).

Purpose: The current onboarding route uses `getUsage()` with a batch-size-only check (`selectedRepos.length > limit`) that does NOT account for repositories already saved in the database. A Free user with 2 existing repos could select 2 more (batch size 2 < limit 3) and end up with 4 repos. Fix: use `getUsage()` properly for batch check (`current + new > limit`) since it correctly returns current DB count and plan limit. Also wire `canAddPrivateRepository()` for private repo enforcement (replaces the inline boolean check).

Output: Repository creation endpoint properly enforces plan limits with correct batch math and canAddPrivateRepository call, with tests proving the fix works for the existing+new repos scenario.
</objective>

    In `POST /onboarding/repositories` handler (around lines 226-292), fix the batch repo limit check and wire canAddPrivateRepository:

    **Why getUsage() is correct for batch checks:** `canAddRepository()` answers "can I add 1 more?" but the route needs "can I add N more?" (batch operation). `getUsage()` returns `{current, limit}` which allows the correct batch math: `current + selectedRepos.length > limit`. For private repos, `canAddPrivateRepository()` is the right method (binary check: is this plan allowed to have private repos?).

    **Replace the current enforcement block (lines 239-276) with:**
    ```typescript
    // Check repository limits BEFORE creating any repos
    // First: check if adding selected repos would exceed limit (accounting for existing repos)
    const usage = await planEnforcementService.getUsage(account._id);
    const totalAfterAdding = usage.repositories.current + selectedRepos.length;
    if (totalAfterAdding > usage.repositories.limit) {
      const errorMessage = `Repository limit reached (${usage.repositories.current}/${usage.repositories.limit}). Upgrade to add more repositories.`;
      return reply.view("onboarding/select-repos", {
        title: "Select Repositories",
        repositories: availableRepos,
        maxRepositories: usage.repositories.limit,
        privateReposAllowed: usage.privateReposAllowed,
        plan: usage.plan,
        error: errorMessage,
      }, { layout: "/layouts/main.hbs" });
    }

    // Second: check if any private repos are selected when not allowed
    const hasPrivateRepo = selectedRepos.some((repo) => repo.private);
    if (hasPrivateRepo) {
      const canAddPrivate = await planEnforcementService.canAddPrivateRepository(account._id);
      if (!canAddPrivate.allowed) {
        return reply.view("onboarding/select-repos", {
          title: "Select Repositories",
          repositories: availableRepos,
          maxRepositories: usage.repositories.limit,
          privateReposAllowed: usage.privateReposAllowed,
          plan: usage.plan,
          error: canAddPrivate.reason,
        }, { layout: "/layouts/main.hbs" });
      }
    }
    ```

    This changes:
    - Repo count check: `selectedRepos.length > limit` → `current + selectedRepos.length > limit` (fixes the gap)
    - Private repo check: `!usage.privateReposAllowed` → `canAddPrivateRepository()` (uses PlanEnforcementService method)
    - Error messages now come from PlanEnforcementService patterns (consistent with service/environment enforcement)
